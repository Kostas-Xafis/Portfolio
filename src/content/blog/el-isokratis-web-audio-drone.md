> **Ενημέρωση, Νοέμβριος 2026:** το άρθρο γράφτηκε για την αρχική PWA και μένει ως καταγραφή εκείνης της δουλειάς. Η PWA έχει πλέον αποσυρθεί. Το Isokratis είναι τώρα εφαρμογή Expo / React Native, που δεν έχει κυκλοφορήσει ακόμη, με την έκδοση Android σε εσωτερικές δοκιμές στο Google Play. Το μουσικό μοντέλο και οι κλάσεις της μηχανής μεταφέρθηκαν εκεί και τρέχουν πλέον πάνω στο `react-native-audio-api`, που ακολουθεί την προδιαγραφή του Web Audio. Η αποθήκευση και η διαχείριση των συνόδων άλλαξαν· οι δύο τελευταίες ενότητες λένε πώς.

Το Isokratis είναι ένα ολοκληρωμένο εργαλείο για κάθε ψάλτη. Ο ψάλτης χρειάζεται ένα σταθερό ισοκράτημα πάνω στο οποίο να ψάλλει, και η εφαρμογή συνθέτει αυτό το ισοκράτημα σε πραγματικό χρόνο, ενώ ο χρήστης επιλέγει κλίμακα και αρχικό φθόγγο. Η ενδιαφέρουσα μηχανική ζει σε δύο σημεία: το μουσικό μοντέλο και το γράφημα ήχου.

## Η θεωρία της μουσικής, κωδικοποιημένη

Η βυζαντινή ψαλμωδία δεν χρησιμοποιεί ισότονο δυτικό σύστημα. Η οκτάβα διαιρείται σε 72 ίσες μονάδες που ονομάζονται **moria**, και κάθε κλίμακα είναι μια ακολουθία διαστημάτων σε αυτό τον χώρο. Έτσι, αντί για σκληροκωδικοποιημένες συχνότητες, το μοντέλο δουλεύει όπως η ίδια η θεωρία:

- 72 moria ανά οκτάβα — συντελεστής συχνότητας 2^(m/72) για m moria
- Επτά φθόγγοι — Νη, Πα, Βου, Γα, Δι, Κε, Ζω — σε σταθερό τονικό κέντρο (Κε = 220 Hz)
- Μια κλίμακα είναι ένα μοτίβο διαστημάτων· το πλέγμα φθόγγων παράγεται **περιστρέφοντας** αυτό το μοτίβο στην οκτάβα

Η επιλογή διαφορετικής κλίμακας αλλάζει μόνο τη λίστα διαστημάτων. Το ύψος προκύπτει πάντα από το τονικό κέντρο μέσω της αριθμητικής των moria, που διατηρεί όλη τη μηχανή συνεπή — και καθιστά τις μικροτονικές μετατοπίσεις φυσικές, επειδή το morium είναι ήδη η ελάχιστη μονάδα.

## Το γράφημα ήχου

Η αλυσίδα σύνθεσης είναι σκόπιμα μικρή και τυποποιημένη:

```
AudioSource → ActiveVoice → DroneEngine → destination
```

Κάθε `ActiveVoice` είναι είτε ταλαντωτής (συνεχής τόνος, μέσω χαμηλοπερατού φίλτρου) είτε δείγμα buffer (ηχογραφημένο ισοκράτημα), που διέρχεται από στάδιο EQ και κόμβο gain με περιβάλλον ADSR. Το `DroneEngine` κατέχει το master gain και εκθέτει γεγονότα (`start`, `stop`, `voicesChanged`) ώστε το UI να μένει συγχρονισμένο χωρίς polling.

Τα σημεία που απαιτούν προσοχή:

- **Μετατόπιση ύψους** σε moria, όχι σε cents: αδρή στα ±6 και λεπτή στα ±1, έως ±36 moria συνολικά. Για ταλαντωτές είναι απλώς `frequency = tonic * 2^(m/72)`· για δείγματα, ο ίδιος λόγος εφαρμόζεται στον ρυθμό αναπαραγωγής.
- **Περιβάλλοντα χωρίς κρότο.** Οι ράμπες attack και release ακούγονται ασήμαντες μέχρι να ακούσεις το pop μιας απότομης αλλαγής gain.
- **Πολυφωνία** στην premium βαθμίδα — πολλαπλές φωνές ταυτόχρονα, καθεμία με δικό της envelope και φίλτρο.

## Αποθήκευση και συγχρονισμός

Στην PWA, οι ρυθμίσεις και τα presets ζούσαν στο IndexedDB ανά χρήστη, που έκανε την εφαρμογή να αισθάνεται στιγμιαία. Στον διακομιστή, μια βάση Cloudflare D1 αποθήκευε λογαριασμούς, συνόδους και premium κατάσταση, και ο συγχρονισμός συσκευών χρησιμοποιούσε stale-while-revalidate: το IndexedDB απαντούσε άμεσα και το API ανανέωνε στο παρασκήνιο.

Η εγγενής εφαρμογή τα κρατά ανά χρήστη σε SQLite. Η D1 εξακολουθεί να κρατά λογαριασμούς, συνόδους και premium κατάσταση, και στον συγχρονισμό συσκευών κερδίζει πλέον η πιο πρόσφατη αλλαγή κάθε εγγραφής.

## Τι με έμαθε η μηχανή

Το Web Audio API είναι εκπληκτικά πλήρες για αυτή τη χρήση — το μόνο που δεν μπορείς να κάνεις είναι να αγνοήσεις τη state machine του audio thread. Κάθε ράμπα gain, κάθε έναρξη φωνής πρέπει να προγραμματιστεί, αλλιώς κροτάει. Αυτή η πειθαρχία μεταφέρθηκε και αλλού: η ίδια φροντίδα φάνηκε στο API της PWA, όπου η επικύρωση συνόδου κρατιόταν σε cache στο Cloudflare KV με TTL. Ο σημερινός Worker έχει καταργήσει αυτή την cache και ελέγχει τις συνόδους στην D1.

Αν ψάλλεις βυζαντινή μουσική, θα βρεις την εφαρμογή στον [ιστότοπό της](https://isokratis.byzantineapps.com) μόλις βγει από τις δοκιμές. Αν γράφεις κώδικα ήχου, η αριθμητική των moria είναι το κομμάτι που θα αντέγραφα.
